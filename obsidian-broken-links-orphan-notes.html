Find broken links, orphan notes and duplicates in your Obsidian vault (free, read-only script)

2026-09-22

A vault that grows for a year or two picks up problems nobody notices until they matter: a link that points at a note you renamed, two notes with the same name so a link opens the wrong one, notes that nothing links to, half the notes missing the properties your queries rely on. Here is what each problem actually means, and how to find them all in one pass without touching your notes.

What to look for

Broken links. A [[Target]] that matches no note. Obsidian shows these as unresolved links, but you only see them one note at a time. Remember that [[Target|alias]], [[Target#Heading]] and links that use a note's aliases: property all resolve to the same note, so a good check has to strip those before matching.

Ambiguous links. The name matches two or more notes, for example Meeting notes in two folders. Obsidian picks one; it may not be the one you meant. This is the most underrated problem because nothing looks broken.

Duplicate note names. The cause of ambiguous links. Rename one, or link with a path ([[20-Areas/Meeting notes]]).

Orphans. Nothing links to the note. Not automatically a problem: inbox notes, reference material and daily notes are often orphans on purpose. Treat orphans as a to-do list for notes you meant to connect, and exempt the folders where orphans are normal.

Missing properties. If a Dataview query or your own filing habits rely on type: or created:, notes without them silently drop out of results.

Stale notes. Not modified for a long time and not archived. Again a prompt to look, not a reason to delete.

Two details that trip up simple scripts

  1. Links inside code (inline backticks and fenced blocks) are examples, not links. A checker that counts them will report false problems.
  2. Line numbers must be file line numbers. If a script strips the frontmatter before counting, every reported line is off by the frontmatter's length and you will land in the wrong place. Count from the top of the file.

Also, file modified times are fragile: unzipping, syncing and git can reset them. If you keep a modified: property, use it; otherwise fall back to the file time and know it may be wrong.

There is a small, dependency-free Python script that does all of the above and never modifies a note. It ships as a free Claude Code skill with a fictional sample vault and tests, so you can also ask Claude to run it, explain the findings, and draft the exact edits for you to approve.
